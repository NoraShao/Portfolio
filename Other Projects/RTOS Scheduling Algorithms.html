FreeRTOS Scheduling Extensions: SRP and CBS

CPSC 538G - Real-Time System Design | January 2026 - April 2026

CPSC 538G was a real-time systems course about the importance of timing in cyber-physical systems. The FreeRTOS project option was to get inside the kernel and extend it with Earliest Deadline First (EDF), Stack Resource Policy (SRP), Constant Bandwidth Server (CBS), and multiprocessor scheduling support. EDF is a dynamic-priority scheduling algorithm that always runs the task with the earliest absolute deadline. SRP is a resource-sharing protocol that prevents priority inversion and deadlock by enforcing a system ceiling on which tasks can run. CBS is a server-based scheduling algorithm that allows periodic tasks to be scheduled with a fixed budget and period, providing temporal isolation between tasks.

The Project: My partner worked on the base EDF and multiprocessor support, and this page is about the SRP and CBS parts I built and tested. I kept EDF as the base scheduler, then added SRP and CBS on top of it in a few specific places: task metadata, admission control, scheduler task selection, semaphore/resource handling, optional stack sharing, and CBS budget/deadline state. The ready list is still ordered by absolute deadline; the extra work is in deciding whether the task at the front is actually allowed to run yet, or whether a server needs its budget/deadline state cleaned up first.

SRP Design

These are some of main design choices I made for implementing SRP:

1. Integrating SRP with EDF: The ready list is still ordered by absolute deadline; EDF says which task is earliest and SRP then decides whether that task is eligible to start now.

2. Deadline-derived preemption levels: Each task's SRP preemption level is derived from its relative deadline (shorter deadline → higher SRP level) via xSRPComputePreemptionLevel(), simplifying translation between EDF and SRP.

3. Central SRP resource table: SRP state is kept in a small kernel-side table with entries for semaphore handle, ceiling, owner, locked state, and blocking time (e.g. srpResources[], systemCeiling, ceilingStack[]).

4. Wrapper semaphores: SRP resource access is explicit through APIs: vSRPRegisterSemaphore(), xSemaphoreTake_SRP(), and xSemaphoreGive_SRP(). Normal semaphores are unchanged.

5. One global live ceiling plus a ceiling stack: Runtime SRP maintains a single systemCeiling and a ceilingStack[] so nested critical sections restore the correct ceiling on release.

6. Admission control includes SRP blocking: The feasibility test adds a single worst-case blocking hit per demand window (SRP model: a job can be blocked at most once before it starts), so task creation computes per-task blocking terms from registered resources and includes them in PDA checks.

7. Stack sharing: Stack sharing is behind configUSE_STACK_SHARING, so I could test SRP without shared stacks first and not be unsure whether I was figuring out a context-copy bug instead of a scheduling bug. For stack-sharing, tasks at the same SRP preemption level share one live execution stack, but each task still has its own saved stack-image buffer.

This is not the most memory-optimal way to do stack sharing, but it is a lot simpler and safer than trying to do a more granular implementation. The stack report separates savings in live execution-stack ranges from savings in overall RAM, which is why the shared-stack version can show good "actual implemented savings" while still showing weak or zero "net memory savings".

CBS Design

CBS was implemented following the algorithm in Buzzatto's Hard Real-Time Computing Systems: Predictable Scheduling Algorithms and Applications; it modifies a server's deadline and remaining budget over time while EDF continues to pick the earliest-deadline ready item.

  • Design overview: CBS state is stored in the TCB: xCBSBudget, xCBSRemainingBudget, xCBSPeriod, xCBSIsActive.
  • xTaskCreateCBS() creates a normal EDF task with C = Q, T = T, D = T and then adds CBS reservation state on top so servers reuse the EDF infrastructure.
  • When a job arrives to an idle server the kernel checks whether the stored (c,d) pair is still valid; if not it refreshes the server to c := Q, d := now + T.
  • While running, the server's budget burns down; when c == 0 the deadline is postponed by one period and the budget refilled.

Runtime and admission: Budget accounting is tick-based in the implementation; when a server's budget hits zero it is postponed and refilled in the tick path. Admission checks reuse the EDF admission path: server utilization is added as Q/T to the total task load.

Tie-breaks: If a CBS server and a normal EDF task share the exact same absolute deadline, the kernel breaks the tie in favor of the CBS server.

Validation and documentation

All tests were run from the RP2040 demo (Demo\ThirdParty\Community-Supported-Demos\CORTEX_M0_RP2040\Standard\main.c) on a raspberry pi. SRP tests were controlled by srp_demo.c and CBS tests by cbs_demo.c, with a TESTCASE selector in each demo.

I used an Analog Discovery 2 logic analyzer (and the WaveForms software) and serial monitor prints to validate timing, resource use, and admission behaviour. The logic analyzer's timing cursors provided good timing verification even if they're not perfectly precise.

SRP validation

SRP validation focused on runtime locking, system ceiling behaviour, admission-control interaction with SRP blocking, and stack-sharing gains. I used GPIO pins to observe which tasks were running at what time, when a shared resource was held, and the live system ceiling via a small binary bus. Critical sections were placed at the end of each job so traces show non-critical work followed by the resource-use window.

Tests included: one shared resource, admission control with SRP blocking time, two shared resources, stack-sharing mode comparisons, constrained-deadline admission checks, and a 100-task stress test to measure stack-sharing gains.

CBS validation

CBS validation checked server replenishment and deadline-postponement behaviour, admission-control both at startup and at runtime, and tie-break behaviour favouring CBS servers when deadlines match. GPIO pins tracked periodic tasks, CBS servers, postpone pulses, and expected/ unexpected admission flags.

Key tests included two periodic tasks with backlogged CBS servers, admission-time rejection of oversubscribed servers, small-budget deadline postponement visibility, and runtime create attempts that demonstrate accept/reject behaviour.
